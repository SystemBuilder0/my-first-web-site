# 영상 자동화 PC 저장공간 실행안 (이 PC 전용)

두 건의 리서치(`YOUTUBER-STORAGE.md`, `CONTENT-FARM-STORAGE.md`)를 이 PC 실측에 적용한 결론입니다.

## 전제 (실측)

- C: 930.9GB / 여유 29.39GB (3.2%) — 901GB 사용 중
- H: SSD 1863GB / **여유 492GB** ← 목적지
- D: SSD 여유 134GB, E:/F: HDD 여유 129GB씩
- RAM 63.9GB, 최대 절전 모드 이미 꺼짐, pagefile 9.5GB
- 확인된 C: 항목: `Windows\Installer` 15.45GB, pagefile 9.5GB, `Windows\Temp` 0.32GB → **합쳐도 25GB**
- **나머지 약 876GB 미확인** — 영상 작업 폴더가 유력

## 1. 이 PC에 클라우드는 지금 필요 없습니다

리서치에서 나온 클라우드 단가(2026-09, 출처는 원문 참조):

| 서비스 | TB/월 | egress |
|---|---|---|
| Backblaze B2 | 약 $6~6.9 | 저장량의 3배까지 무료 |
| Cloudflare R2 | 약 $15.36 | 무료·무제한 |
| AWS S3 Standard | 약 $23 | 최대 $90/TB |

**이 PC는 로컬에 1TB 넘는 빈 SSD/HDD가 있습니다.** 작업 저장소를 클라우드로 옮기면 연 $72~180/TB를 내면서 속도는 로컬 SSD보다 느려집니다.

클라우드가 의미 있는 지점은 **3-2-1 백업의 "오프사이트 1벌"** 하나뿐입니다. 화재·도난·랜섬웨어 대비용이며, 작업 저장소 대체재가 아닙니다. 그마저도 지금은 C: 포화를 푸는 게 먼저입니다.

## 2. "유튜브 공장은 클라우드를 쓴다"는 통념 — 근거가 약합니다

리서치의 중요한 발견은 **부정적 발견**이었습니다.

- 다채널 대량 운영자가 스토리지를 어떻게 관리하는지 밝힌 **신뢰할 만한 1차 실사례가 거의 없습니다.** 검색 결과 대부분이 코스·템플릿 판매용 마케팅 페이지였습니다.
- 실제로 코드가 공개된 오픈소스 자동화(`yt-faceless-automation`, GitHub 원문 확인)는 **클라우드가 아니라 "슬러그별 로컬 디렉터리 + FFmpeg 로컬 렌더링"** 구조입니다.
- 따라서 "클라우드 우선이 이 업계 표준"이라고 단정할 근거는 확인되지 않았습니다.

판매 콘텐츠의 주장(예: 특정 인물의 "20개 채널 20억뷰")은 검증되지 않았으므로 의사결정 근거로 쓰지 마세요.

## 3. 실제로 검증된 것 — 자동 정리(retention)

반면 **자동 정리 패턴은 실사례가 명확합니다.** 이게 이 PC에 필요한 것입니다.

| 사례 | 내용 | 출처 성격 |
|---|---|---|
| n8n 템플릿 | R2 파일 중 **14일 지난 것 매일 자동 삭제** + 텔레그램 알림 | 마켓플레이스 실제 등록 템플릿 |
| n8n 템플릿 | S3 백업 **보존기간(기본 31일) 후 자동 삭제** | 동일 |
| 범용 cron | `find <dir> -type f -mtime +N -delete` | FFmpeg 임시파일 정리 표준 관행 |
| GitHub Actions | `retention-days` 파라미터 (기본 90일) | 공식 문서 |
| ComfyUI | `ComfyUI-TempFileDeleter` 커스텀 노드 존재 | GitHub 실존 |

공통 구조는 **"스케줄 + 나이 필터 + 삭제"** 입니다. 도구가 무엇이든 이 셋이면 됩니다.

n8n 커뮤니티에는 "30분마다 파일을 받아 업로드하는데 쌓여서 디스크 부족 에러가 난다"는 실제 문제 제기가 있고, 해결책은 **"업로드 후 받은 파일을 삭제하라"** 였습니다. 자동화 파이프라인이 정리 단계를 빠뜨리는 것이 전형적 실패 모드입니다.

## 4. 실행 순서

### 4-1. 편집 캐시부터 (가장 큰 단일 항목일 가능성)

리서치에서 확인된 수치:

| 항목 | 누적 크기 | 자동 정리 |
|---|---|---|
| Resolve Optimized Media | 200~400GB (2시간 4K 타임라인) | 없음 |
| Resolve Render Cache | 20~40GB | 없음 |
| Premiere Media Cache | 50~150GB | 불완전 |

Resolve는 Render Cache / Optimized Media / Proxy Media / Gallery Still / Fusion 캐시를 **각각 다른 폴더에 따로** 쓰며 **어느 것도 자동 정리되지 않습니다.** 기본 위치는 첫 번째 등록 스크래치 디스크이고, 바꾸지 않았다면 C:입니다.

**조치 — 캐시 위치를 H:로 이전**

- Resolve: 환경설정 → Media Storage의 첫 항목을 `H:\cache\resolve`로. 프로젝트 설정 → Master Settings → Working Folders에서 캐시/프록시 경로 확인
- Premiere: 편집 → 환경 설정 → 미디어 캐시 → 위치를 `H:\cache\premiere`로 변경 후 "사용하지 않는 항목 삭제"

캐시는 재생성되므로 **되돌리기 부담이 없는 유일한 대형 항목**입니다. 여기부터 하세요.

### 4-2. 프록시 워크플로 도입

원본 대신 저해상도 대체본으로 편집하고 최종 출력 때만 원본을 씁니다. **90~95% 절감**이 보고되며 Premiere·Resolve 모두 내장 기능입니다.

- 편집 반응성 우선 → ProRes Proxy
- 용량·이동성 우선 → H.264

### 4-3. 스크래치 디스크 분리 (성능 + SSD 수명)

OS 드라이브와 분리하는 이유는 성능만이 아닙니다. 영상 작업은 수백 GB를 쓰고 지우기를 반복해 **SSD의 TBW(총 쓰기량)를 갉아먹습니다.** 별도 드라이브로 분산하면 C: SSD 수명이 늘어납니다.

이 PC는 H:가 SSD라 최적입니다. **E:/F:는 HDD이므로 캐시·스크래치 용도로 쓰지 마세요.**

### 4-4. 파이프라인에 정리 단계 추가

자동화 스크립트에 "업로드/렌더 완료 후 중간 산출물 삭제"를 넣습니다. 없으면 Windows 작업 스케줄러로 주기 실행:

```powershell
# 중간 산출물 폴더에서 N일 지난 파일 삭제 (경로·일수는 환경에 맞게)
$dir  = 'H:\work\_intermediate'
$days = 14
Get-ChildItem $dir -Recurse -File -EA SilentlyContinue |
  Where-Object { $_.LastWriteTime -lt (Get-Date).AddDays(-$days) } |
  Remove-Item -Force -WhatIf    # 확인 후 -WhatIf 를 빼고 실행
```

> `-WhatIf`가 붙어 있으면 **삭제하지 않고 대상만 보여줍니다.** 목록을 먼저 확인하고, 맞으면 그때 빼세요.

### 4-5. 보관 기간 정하기

리서치 결과 **원본 보관 기간에 업계 표준은 없습니다.** 30일~2년으로 제각각이고 "계약에 명시 없으면 결국 삭제"가 관행입니다. 즉 이건 기술 문제가 아니라 **본인이 정하는 정책**입니다.

권장 출발점:

| 대상 | 보관 | 위치 |
|---|---|---|
| 편집 캐시·프록시 | 프로젝트 종료 시 삭제 | H: (재생성 가능) |
| 중간 산출물 (프레임 시퀀스, 실패 생성본) | 14일 | H: → 자동 삭제 |
| 소스 푸티지 | 채널 운영 중 보관 | F: (HDD로 충분) |
| 최종 업로드본 | 영구 | F: + 오프사이트 1벌 |

## 5. 하지 말 것

- 클라우드로 작업 저장소를 옮기는 것 — 로컬 SSD 여유가 1TB 넘게 있는데 돈을 내고 느려집니다
- 판매용 "유튜브 자동화 코스"의 스토리지 주장을 근거로 삼는 것 — 검증된 1차 자료가 아닙니다
- `C:\Windows\Installer` 직접 삭제 — 프로그램 제거·복구가 깨집니다
- 정리 스크립트를 `-WhatIf` 확인 없이 바로 실행하는 것
